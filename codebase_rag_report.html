Architectural Decisions & Motives

Every decision in this RAG and Agent pipeline was made to combat real-world codebase limitations such as semantic dilution, LLM hallucinations, and execution failures.

1. AST-Based Structural Chunking

Decision: Use Tree-sitter to parse the Python AST and chunk code at the method-level (rather than class-level or fixed-character sliding windows).

Motive: Massive files dilute embeddings. A 1,900-line class compresses 22,000 tokens into a single vector, making it impossible to retrieve precise semantic functions. Character windows, conversely, break Python syntax mid-function. Method-level chunking preserves structural context while drastically shrinking average chunk size to 422 tokens, ensuring high-fidelity retrieval.

2. Hybrid Search with Reciprocal Rank Fusion (RRF)

Decision: Combine dense vector embeddings (ChromaDB + Nemotron) with sparse exact match algorithms (BM25).

Motive: LLMs struggle to map abstract queries ("how do we handle tokens?") to specific programmatic identifiers ("AuthValidatorImpl.token"). Dense search captures the abstract meaning, while BM25 handles exact variable lookup. RRF fusion ensures the best of both worlds bubble to the Top-20 retrieved code chunks.

3. Grounding Critic Isolation (Mode A)

Decision: The Verifier Node only sees the final proposed answer and the raw retrieved code chunks. It does not see the intermediate thoughts or failed tool calls of the Reasoning Node.

Motive: Unbiased evaluation. If the Critic sees the Reasoning Node "thinking" and convincing itself that a hallucinated endpoint exists, the Critic might agree. By isolating the Critic to strictly raw code vs. final answer, we guarantee a zero-hallucination verification.

4. Sandboxed Execution Validation (Mode B)

Decision: Generated code patches are tested using a dynamically generated `pytest` script inside a bounded, short-lived subprocess (`tempfile`).

Motive: Zero Regression Guarantee. LLMs generate code with missing imports, indentation errors, or logic regressions. Executing untrusted AI code directly on the host is a security risk. The sandbox ensures we only present fixes that provably pass the test without destroying the host system.

5. Dynamic Syntax AST Pre-Check

Decision: Run `ast.parse()` on the LLM's fix string before attempting to run it in the sandbox.

Motive: LLMs frequently mess up Markdown code block formatting or Python indentation. The AST check catches these immediately and feeds the error back to the node for self-correction, saving costly and slow subprocess execution time.

Multi-Model Allocation Stack

Transitioned from monolithic models (like GLM-5.2 everywhere) to a specialized, multi-LLM architecture to maximize speed, intelligence, and accuracy. This prevents infinite ReAct loops and 404 errors observed in earlier ablation trials.

Execution Verifier minimaxai/minimax-m3 Robust Test Generation: Needs to synthesize edge-case heavy pytest scripts and interpret raw stderr tracebacks. Minimax M3 easily adapts test cases and iterates effectively on feedback from the sandbox.

Sandbox & Retry Logic Implementations

Recent architectural updates significantly enhanced the agent's resilience by introducing dynamic retry loops at critical failure points.

  • Verifier Hallucination Backoff: If the thinkingmachines/inkling critic detects an ungrounded claim, it rejects the answer and sends the specific reason back to the reasoning_node to conduct another search.
  • AST Syntax Retry: If minimaxai/minimax-m3 outputs a syntactically invalid Python block (e.g. missing indent), the node catches the SyntaxError instantly and retries the generation up to 3 times automatically.
  • Pytest Sandbox Failures: If the isolated pytest execution fails (pre-fix or post-fix), the raw stderr stack trace is captured and sent back to the agent as feedback, triggering a self-correction loop where the model writes a new patch based on the failing tests.
